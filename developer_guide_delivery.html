20 · 测试分层、执行命令与验收

层现有位置 / 作用典型失败定位
unitautodiff、geometry、conditions、metrics、registry 等单组件公式、形状、法向、参数边界
contractpublic API、config、method catalog、output、multi-field接口破坏或字段缺失
smoke问题/方法/几何短训练、生成器运行组件单独可用但组装失败
regressionseed、checkpoint resume、reference leakage重复性、状态或训练参考泄漏
methods各变体算法与比较约束某具体变体行为变化
jsNode 环境几何解析/编辑算法图片/DXF 纯函数错误

依赖与首次运行先按第 1.1 节准备；以下顺序保证 DOM 测试读取的是当前 HTML。npm test 运行本项目的 tests/js/*.test.cjs，既含纯算法检查，也含 jsdom 事件联动检查。

python scripts/build_docs.py
node -e "require('jsdom')"
npm test
python -m pytest -q -ra
node --check docs/_static/method_configurator.js
python -m pip freeze

完整 pytest/验证脚本可能比 targeted tests 花费更多时间，不要在不知道预算时把全方法比较当作每次样式修改的默认命令。可优先运行：

python -m pytest -q tests/contract tests/unit/test_reference_data.py
python -m pytest -q tests/smoke/test_custom_equation_configurator_smoke.py tests/smoke/test_dxf_import_runtime.py
python -m pytest -q tests/regression/test_checkpoint_resume.py
node --test tests/js/dxf_geometry_import.test.cjs

页面验证不能仅靠源码包含字符串

  1. 检查 HTML 中 JS 查询的 data-role 实际存在。
  2. 在 DOM 测试或可访问浏览器中设置真实字段并派发实际事件。
  3. 导入有效、无效、空、过大及支持边界条件的文件。
  4. 检查 SVG 标签与代码数值同时更新，而不仅是提示文字更新。
  5. 把生成 Python 编译并执行小预算训练；读取产物确认生效。
  6. 测试浏览器缩放、窗口尺寸、键盘操作与孔洞切换。DOM 无布局环境的通过不能替代真实视觉/拖拽测试。

本双说明书的具体校验结果单独写入 manual_validation.json，不要把历史 FINAL_VALIDATION.md 的结果冒充本次重新执行。任何 5 步 smoke 只证明链路，不证明精度、收敛、普遍适用或论文复现。

提交与审阅：让别人能够验证你的贡献

本节面向计划发布到 GitHub 后的协作。当前本地目录未提供已配置的远程仓库或 CI 保证；下面是建议流程，不是声称已启用的自动门禁。不会因阅读本说明而自动创建 Issue、推送分支或合并 PR。

贡献者：提交前组织好证据

  1. 从发布后的实际仓库获取工作副本；无写权限时使用自己的 fork，有权限时按仓库约定建功能分支。不在说明书中猜测仓库地址、默认分支或审阅人。
  2. 一次 PR 聚焦一个目标。新算法或破坏性变更先关联讨论记录；小修复说明复现即可，不要求人人先提交长篇设计。
  3. 检查变更列表：不要把个人路径、原始敏感数据、node_modules、虚拟环境或大批实验输出混入提交。生成文档/站点是否纳入版本库，由未来仓库政策统一决定。
  4. 执行受影响层测试，记录真实命令和通过/失败/跳过；共享版本前补完整回归。已有失败与本次新增失败分别列出，不通过删测试“修复”。
  5. 更新相关示例、使用说明和开发契约，解释旧调用、YAML、checkpoint、边界编号是否改变；必要时提供迁移示例。
  6. 提交 PR 后响应审阅；追加修改后重跑受影响检查。PR 合并与版本发布是不同动作，是否发布由维护者决定。

可以直接使用的 PR 描述骨架

目的与关联：解决的 Issue / 提案；本次不做什么
复现：最小输入、命令或页面操作；修复前与修复后
实现：关键文件和选择该扩展点的理由
接口影响：默认值 / API / 配置 / 输出 / checkpoint；兼容或迁移方式
验证：环境、命令、退出码、通过/失败/跳过；尚未检查的项目
数值主张：仅链路验证，或附公平比较条件与原始结果
文档与示例：已更新的入口和运行方式
来源与依赖：公式、参考实现来源、新依赖和许可状态
风险与回退：可能受影响的旧路径；可独立撤销的修改范围

维护者：按四个问题审阅

  • 是否解决真实任务？能否使用提交的输入重现旧问题并验证新行为；范围有没有扩张？
  • 是否放对位置？算法是否在公共组件，配置是否只负责组装，前端和后端契约是否一致？
  • 是否破坏已有用户？旧配置、默认值、产物和状态恢复有没有明确结果；失败路径是否仍清晰？
  • 证据是否支持主张？短跑只能证明执行链；精度/效率改进需要相应数值比较。未测的平台和交互必须留下限制。

证据不足时说明需要补什么并返回修改，不要求作者用模糊的“全部正常”替代结果。合并后保存变更说明；出现回归时先记录影响和复现，采用可追溯的修正或回退，不删除用户实验数据。

仓库公开前，由项目负责人确认

本地 LICENSE_STATUS.md 明确仓库级软件许可证尚未确定。公开前应由负责人确定许可选择，并核对 THIRD_PARTY_NOTICES.md、代码/数据来源及可分发范围；本次文档修改不替负责人作许可决定。

还需确定实际仓库地址、贡献入口、维护者联系渠道、受支持环境、生成产物策略、版本号来源和发布责任。Issue/PR 模板、CI、分支保护、贡献者协议等是否需要及如何配置，应由维护者决定；当前说明书只提供流程和内容建议，不宣称这些设施已经落地。

首次发布后可将本指南链接到仓库 README / CONTRIBUTING 入口，避免维护两份互相矛盾的规则。每次公共接口变更同步本指南、示例与版本记录；不要仅靠更新网页截图宣布完成发布。

21.2 改接口前的影响检查

  1. 先写旧契约和新契约：字段名、类型/张量形状、单位、默认值、异常、状态序列化有何差异。
  2. 用代码搜索定位直接调用、registry 工厂和生成字符串；静态调用附录不能覆盖全部回调/多态/模板引用。
  3. 规定旧调用如何继续使用：保持默认、提供兼容别名、明确拒绝并给迁移示例，三者不能含糊混用。
  4. 为旧路径和新路径分别留测试。几何重编号必须用不同边界值检查错配，全部取零会掩盖错误。
  5. 审阅时同时看后端代码和生成脚本，不把两者分开签署为互不相关的改动。

文件与关键函数：变更落点、消费者、是否修改公共契约
复现输入：项目内样例路径 / 获取方式 / 文件哈希 / 使用许可
环境：OS、Python、PyTorch、Node、npm、依赖清单
验收：命令 + 退出码 + passed/failed/skipped + 每个必要 skip 的处理
界面检查：浏览器版本、缩放、拖拽、键盘、回退；未做就写未做
数值证据：链路 smoke / 独立参考 / 收敛 / 多种子，明确本次属于哪一级
兼容与迁移：旧脚本、YAML、checkpoint、几何编号各自结果
交付：页面、双说明书、build_report、validation、压缩包路径
回退：可撤销变更范围或上一完整工作副本；已有实验数据保持不动
遗留问题：限制、下一步、跟进负责人

案例输入应放在项目中或提供可获取的位置，不以个人桌面的绝对路径作为唯一复现条件。敏感或无再分发权的 CAD/参考数据不得直接打包；提供匿名化最小复现样例。多人同时改配置器大文件时，先约定修改函数范围和共同状态契约；仅减少文本冲突不能避免状态逻辑冲突。

22 · 文件安全、资源限制和已知边界

  • 不可信 Python：问题工厂是代码执行入口，不是数据文件导入器，只运行可信内容。
  • YAML：使用 safe_load，不要改成可执行任意对象的加载器。
  • 浏览器导入：目前文件在本地读取；保持文件大小、顶点数量、像素上限与错误提示。不要未经用户同意改为上传到外部服务。
  • HTML/SVG：用户文本必须经 pythonLiteral/escapeXml 等正确序列化；新增文件名、标签和公式显示时评估注入风险。
  • 资源消耗：高分辨率图片、复杂相交检查、大候选池、二阶导数和 L-BFGS 都有成本，不提供“无限精度”开关。
  • 不支持的能力：MPH/DWG 原生解析、通用 3D CAD、多不连通域、页面周期边界、任意耦合系统可视化并未由当前配置器完整提供。
  • 数学适定性：前后端合法性检查不等于 PDE 存在唯一解，纯 Neumann、初边值冲突和二阶时间初始速度仍需问题负责人判断。
  • 图像识别：像素轮廓拟合存在误差；DXF 短边拟圆有容差。物理尺寸应来自工程坐标而不是截图比例推断。

发布前查看 LICENSE_STATUS.md 与 THIRD_PARTY_NOTICES.md。不能因为本项目名含 Open 就推断所有算法/数据/依赖都允许任意商业再发布。

23 · 双说明书构建、更新与交付

两份手册的人工正文分别在 docs/manuals/_sources/user_content.html 和 developer_content.html。scripts/build_manuals.py 负责加入统一离线样式/目录脚本、方法完整参数表、Python AST 索引、JS 命名函数定位和快照哈希。

23.1 推荐统一入口

python scripts/build_docs.py

scripts/build_docs.sh、scripts/build_docs.ps1 以及 check 脚本的文档阶段均转到这个入口。使用运行入口的同一个 Python 解释器，按顺序执行下列步骤；任一步骤返回非零即停止，后续阶段不继续，不更新交付压缩包。

build_manuals.py：读取正文与当前源码，生成独立 HTML、函数索引和快照
 → validate_manuals.py：结构/链接/JS 语法/标记 Python 示例检查与短运行
 → sphinx -E -a -W --keep-going：从当前独立 HTML 嵌入站内版并复制静态资源
 → 打包 docs/manuals/OpenPINN_双说明书_<快照日期>.zip

最后的 ZIP 包含两份独立 HTML、manual_build_report.json 和 manual_validation.json；同一快照日期重复构建会更新同名包。失败后旧文件或部分新构建文件仍可能存在，不能仅凭文件存在或浏览器还能打开就认定交付成功。只有整个命令退出码为 0 才表示本次流水线完成。

23.2 分步排错，不把低层命令冒充完整交付

python scripts/build_manuals.py
python scripts/validate_manuals.py
python -m sphinx -E -a -W --keep-going -b html docs docs/_build/html

以上分步命令用于定位哪一阶段失败，不包含最终压缩包更新。直接运行 Sphinx 仍只会读取已经生成的 public 内容；正文改动后只运行 Sphinx 可能得到旧手册。日常交付优先使用统一入口。

生成目标为 docs/manuals/public/user_manual.html 和 developer_manual.html；Sphinx 把该 public 目录中的文件拷入 HTML 站点。单个文件内含全部样式和交互脚本，无 CDN。一起复制两份 HTML 可保留相互切换链接。

站内入口 user_guide.rst、developer_guide.rst 为总览页，各自通过 toctree 连接 6 个独立子页面。docs/_ext/manual_sections.py 统一定义分组，扩展 openpinn_manuals.py 依据分组抽取独立 HTML 的正文、验证完整覆盖并重写跨页链接。新增节必须分配到唯一子页；改分组时同步对应 rst 标题和 toctree。旧总览页的章节锚点在启用 JS 时自动转到新页面。本页内容导航默认折叠，小节高亮由 URL 片段决定；Sphinx 左侧导航标示当前子页面。独立版仍为离线完整文件，但目录按相同的 6 组折叠。分页、正文链接、函数检索和两种版本均需回归。

validation 脚本校验结构/内链/示例语法并在隔离临时目录运行标记为 smoke 的短样例；不执行手册中所有任意命令，也不代替完整 pytest。生成索引需使用当前源码的可编辑安装或脚本插入的 src 路径，避免索引元数据来自旧 wheel。

23.3 构建完成不等于所有验收完成

统一入口执行手册验证和 Sphinx，但不隐含 npm test、完整 pytest、真实浏览器视觉检查或正式收敛实验。交付者按第 21.1 节补齐受影响层的证据。Windows PowerShell 包装脚本与 Python 主入口职责相同；平台实测结果应单独记录，不因 macOS 通过而宣称 Windows 已通过。

保持准确性的规则

  1. 源码变更后重建函数索引和哈希，检查正文是否也需修改；自动索引不会自动改写人工解释。
  2. 版本变更时同步编写基准日期与元数据，不只改标题。
  3. 函数行号会随改动变化；不要把旧 HTML 的行号当成新代码位置。
  4. Sphinx 扩展变更使用 -E -a 强制重建，避免旧 HTML 缺字段却加载新 JS。
  5. 验证通过信息必须来自本次实际命令，保留失败与未检查项目。

23.4 发布前核对表

  • 正文里的实现声明已经对照本次源码，附录哈希已刷新。
  • Node 测试依赖使用 package-lock.json；Python 实际依赖版本随交接记录提供。
  • 统一构建退出码为 0；manual_validation.json 中 status 为 passed。
  • 总览可进入正确子页面，各站内子页与独立 developer_manual.html 合计包含全部正文，无重复遗漏。
  • ZIP 中 HTML/报告与 public 同名文件一致，不能使用上次下载的旧包。
  • 打开的是本次 docs/_build/html 而非历史 dist，刷新缓存后再做界面验收。
  • 测试结果、skip、未测平台和已知限制一起交付；功能升级是否需调整版本号由发布负责人决定。

23.5 离线正文搜索的维护

docs/_ext/openpinn_search.py 在 HTML 构建成功后读取当前文档的 itemprop="articleBody" 正文，按标题划分小节，写入 _static/openpinn_search_index.js。这样原始 HTML 形式嵌入的说明书也进入索引；每次均按当前文档列表重建，避免增量构建遗漏未变更页或保留已删除页。索引是本地脚本资源，不通过 fetch 读取文件。

docs/_templates/search.html 替换搜索页，docs/_static/documentation_search.js 完成中文/英文子串匹配、多个关键词同时匹配、标题排序、摘要、分页和小节链接。它不是语义搜索或拼写纠错，也不依赖 jieba；变更匹配规则须保留“圆孔”“固结”“固结系数”和 API 名称的回归。扩展移除上游 sphinx_highlight.js；自己的高亮只处理静态 HTML 正文，不改 SVG、数学节点、代码或配置器控件，以免破坏图和生成代码。

检查入口：tests/unit/test_documentation_search.py 验证正文提取、增量重建和脚本替换；tests/js/documentation_search.test.cjs 验证实际生成索引、摘要、分页、高亮及输入安全。发布前还需在真实浏览器用 file:// 和 HTTP 检查搜索结果跳转，确认无网络依赖、无脚本报错、配置器仍可生成代码。改动文档后运行统一构建，不能只复制旧索引。
